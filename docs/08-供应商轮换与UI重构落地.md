## 一、Codex 核心配置文件精简架构（已完成归一合并）

原有的历史遗留文件 `cc-switch-model-catalog.json` 已被彻底移除，所有自定义模型（包括当前活跃的 `k3`）已完整迁移并合流至根目录的原生 `models.json`。目前 Codex 与网关的配置链路清晰直观：

```
C:\Users\gg1\.codex\
├── config.toml         # [主控] 声明活跃模型（model = "k3"）、供应商、指向 models.json
├── auth.json           # [鉴权] 本地 Codex 客户端请求网关时携带的 Bearer 密钥
├── models.json         # [元数据] 官方与自定义模型规范池（已含 k3、deepseek-v4、MiniMax）
└── tools/
    ├── bridge_config.json  # [路由] 网关转发配置（上游地址、端口、多Key池及自动容灾开关）
    └── bridge_stats.db     # [数据] SQLite 请求历史与性能统计
```

### 各文件职责与轮换时的联动原则

| 配置文件 | 关键字段/当前内容 | 轮换时触发的行为 |
| :--- | :--- | :--- |
| **`config.toml`** | `model = "k3"`<br>`model_catalog_json = "models.json"`<br>`model_context_window = 1000000` | **模型切换生效点**：当用户在 UI 下拉选择新模型（如 `k3` 切换为其他模型）时，网关通过安全局部正则替换更新 `model` 字段，保持用户原有的信任项目目录（`[projects]`）和插件不受破坏。 |
| **`auth.json`** | `{"OPENAI_API_KEY": "sk-kimi-..."}` | **当前活跃密钥鉴权**：在多 Key 轮换池中切换或轮询选择有效 Key 时，以原子文件替换方式同步写回，确保 Codex 原生发起请求时鉴权一致。 |
| **`models.json`** | `{"models": [{"slug": "k3", ...}, {"slug": "deepseek-v4-flash", ...}]}` | **模型规格池**：用户在设置界面添加新模型时，将自动在此注册模型标准协议元数据（上下文尺寸、工具适配、代码补丁类型），保证 Codex 客户端能顺利初始化。 |
| **`tools/bridge_config.json`** | `"upstream": "https://api.kimi.com/coding"`<br>`"providers": {...}` | **多供应商与 Key 轮换中枢**：存储主备供应商配置、多 Key 列表、健康检查缓存以及 `auto_failover`（遇 403 自动热切备用 Key）开关。 |

## 三、代码落地工作分解（供审批后执行）

   - 增加 `/dashboard/api/provider-keys` 接口，负责安全提取与原子覆写 `auth.json`、`config.toml` 与 `models.json`；

## 四、安全与保全机制

* **写入安全**：全部采用临时文件原子写入（`os.replace`），修改前后自动保留最新一个 `.bak` 快照。
* **隔离保护**：只触碰必要配置字段（`model`, `model_catalog_json`, `OPENAI_API_KEY`），完全不影响 `config.toml` 内大量已信任的开发目录（`[projects]`）和系统插件配置。
