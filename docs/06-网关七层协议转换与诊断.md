# 诊断记录：Codex ↔ Kimi 协议差异全景

2026-08-22 在一台 Windows 11 机器上逐层挖出并修复。每层都附 Kimi 的报错原文与根因。四层是**递进发现**的——修一层才暴露下一层。

## 第 0 层：环境劫持（与协议无关但最先迷惑人）

- Codex 进程**缓存 base_url**：改了 `config.toml` 不重启进程，旧地址还在用。表现为端口无人监听后 1.3 秒秒挂 `{"error":{"message":"Invalid request Error"}}`。
- **cc-switch 的"退出恢复"不等于回官方**：它退出时把配置恢复到*接管前*状态；接管前选中的是 Kimi provider，恢复完还是 Kimi。且它注册了开机自启 + "下次启动自动恢复接管"，重启后会再次改写 `config.toml` 指向它的代理（默认 `127.0.0.1:15721`）。
- 加速器（如中本加速 zhongben）用 Wintun TUN + fake-ip DNS 接管 `api.kimi.com` / `api.anthropic.com` / `api.openai.com` 全部流量。排查"连不上"时先 `Resolve-DnsName` 看解析到的 IP——`198.18.0.x` 就是 fake-ip，流量在走隧道。

## 第 1 层：工具 schema 缺 `type`

**报错**：`tools.function.parameters.type is required and must be "object"`

**根因**：Codex 发出的部分工具（动态工具如 `list_projects`，空 schema `{}`）`parameters` 缺 `"type":"object"`。OpenAI 容忍，Kimi 严格校验。

**修法**：桥接请求路径给所有 function 工具的 `parameters` 补 `"type":"object"`。

> 注：2026-08-22 下午实测 Kimi 已不再拒绝此形状（服务端疑似修复），但桥接仍保留该补丁，无害。

## 第 2 层：Kimi 不认识的工具类型

**报错**：`invalid_request_error: tools.14: tool type "tool_search" is not supported`

**根因**：Codex 0.149 的 tools 数组里有 `{"type":"tool_search"}`、`{"type":"web_search"}`、`{"type":"namespace","name":"codex_app","tools":[...]}` 这些非 function 类型。Kimi 只认 `function`。

**修法**（请求路径 tools 改写）：
- `tool_search`/`web_search` → 等价 function（附合理的 parameters schema，见 `SPECIAL_PARAMS`），**并在响应路径把它们还原成原生项**（见第 4 层）
- `namespace` → **展平**：成员工具逐个变独立 function（裸名），同时学习 `工具名→namespace` 映射
- 其余未知类型 → 转 function 形式，description 标注原类型

## 第 3 层：对话历史里的原生条目

**报错**：`{"error":{"message":"Invalid request Error","type":"invalid_request_error"}}`（上游 400，无详细原因）

**根因**：桥接了第 2 层后，app 能执行 `tool_search`（客户端执行），但**下一条请求**的 `input` 数组里带上了调用记录——原生格式是 `tool_search_call`/`tool_search_output` 这些 Kimi 不认识的条目类型。此时 app 的表现是把客户端工具调用标记为 **aborted**。

app 原生格式（从 rollout 文件挖出的铁证）：

```json
{"type":"tool_search_call","id":"tsc_...","call_id":"tool_...","status":"completed","execution":"client","arguments":{"limit":3,"query":"..."}}
{"type":"tool_search_output","id":"tso_...","call_id":"tool_...","status":"completed","execution":"client","tools":[{"type":"namespace","name":"codex_app","tools":[{"type":"function","name":"create_thread","defer_loading":true,...}]}]}
```

注意：`arguments` 是**对象**；结果在 `tools` 字段；工具带 `defer_loading:true`。

**修法**（请求路径 input 改写）：所有 `*_call` → `function_call`（arguments 字符串化）、`*_output` → `function_call_output`（output 字符串化；`tool_search_output` 的结果从 `tools` 字段提取）。同时剥离 `function_call` 上的 `namespace` 字段（Kimi 不认）但把映射学下来。

## 第 4 层：响应路径的原生项还原

**报错**：app 侧 `unsupported call: web_search`（分发器原话）；`tool_search` 调用返回 `aborted`。HTTP 全程 200，日志无异常。

**根因**：第 2 层把特殊工具转成了普通 function，Kimi 回的自然是普通 `function_call`。但 Codex app 的分发器**只认原生特殊项类型**才走客户端执行——收到叫 `web_search` 的普通 `function_call` 直接拒发。

**修法**（响应路径 SSE 改写）：
- `function_call` 的 name 属于被转换的特殊工具时，**缓冲**其 `output_item.added` → `function_call_arguments.delta×N` → `done` → `output_item.done` 全部事件
- 完成后合成原生项（arguments 解析回对象、补 `execution:"client"`、`status:"completed"`），以 `output_item.added` + `output_item.done` 两个事件发出
- `response.completed` 的 `response.output` 数组同步替换；`sequence_number` 重排保持单调
- 动态工具（namespace 成员）的 `function_call` 回填 `"namespace"` 字段（app 按此分发 DynamicToolCall）

## 第 5 层：延迟加载契约（deferred loading）

**报错**：无 HTTP 错误。模型在文本里"看得见"搜到的工具 schema 却无法绑定调用，退化为 `echo "placeholder"` / `echo retry` 空转。

**根因**：`tool_search` 的契约是"搜到的 deferred 工具在下一次调用时变成真正可调用的工具"。OpenAI 原生链路这个"曝光"由**服务端**完成；Kimi 没这概念，桥只学了映射没注入工具。

**修法**（请求路径工具注入）：转发前扫 `input` 里的 `tool_search_output`（含完整工具 JSON），把 deferred 工具扁平化（去 `defer_loading`、补 `parameters.type`）后 merge 进本次 `tools` 数组（按名去重）。无状态——每条请求自带全量历史，桥重启不丢。

## 第 6 层：`$ref` + 兄弟字段的 JSON Schema

**报错**：`tools.function.parameters is not a valid moonshot flavored json schema, details: <At path '$defs.__schema20': when using $ref, type should be defined in the referenced schema instead of the parent schema>`

**根因**：Codex 的 schema 生成器会发 `$ref` 与 `description` 等兄弟字段并列的写法（JSON Schema 2020-12 合法），如 automations 类工具：

```json
"__schema5": {"description": "...name...", "$ref": "#/$defs/__schema2"}
```

Kimi 的校验器（moonshot flavored）拒绝。

**修法**：schema 消毒器 `sanitize_schema()`——递归内联 `$ref`（兄弟字段优先，符合 JSON Schema 与语义），纯 `$ref` 一并展开，循环引用回退 `{"type":"object"}`，`$defs` 块用完即删。接入所有工具入口（普通 function、namespace 展平、deferred 注入）。

## 第 7 层：孤儿工具调用（web_search 的服务端语义）

**报错**：`an assistant message with 'tool_calls' must be followed by tool messages responding to each 'tool_call_id'. The following tool_call_ids did not have response messages: web_search:0`

**根因**：`tool_search` 是 `execution: client`（app 执行并回传 `tool_search_output` 结果项），而 `web_search` 是**服务端语义**——app 收到桥合成的 `web_search_call` 后只记录、不执行、不产生结果项（OpenAI 原生链路上结果由服务器嵌在响应里）。历史里留下没有结果配对的调用，桥转成 `function_call` 后就成了孤儿 tool_call，Kimi 的 chat-completions 风格校验器拒绝整条请求。

**修法**（input 路径·孤儿修复 `repair_orphan_calls()`）：转换完历史条目后做配对检查——任何 `function_call` 找不到同 `call_id` 的 `function_call_output`，就合成一个占位结果项，并**明确告诉模型真相**（web_search 结果不经桥回传，改用 exec_command/curl 或凭知识回答），让模型立刻换路而不是反复尝试。只在缺失时补，`tool_search` 等正常配对不受影响。

**衍生认知**：web_search 在此桥接下实际不可用（无搜索后端），模型会收到占位说明后优雅降级。若未来要真正支持，需要桥接自己执行搜索（接搜索 API）——暂未实现。

## 排障方法论（可复用）

1. 桥接日志是单一事实来源：每个请求的 tools 全量抓包 + input 条目类型摘要 + 每次转换/注入 + 上游状态码与 400 原文
2. Codex 的 rollout 文件（`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`）里有 app 的原生 wire 格式——**遇到不知道的格式去 rollout 里挖实证**，不要猜
3. 对照实验三件套：直连 Kimi（复现 400）→ 过桥（应 200）→ 单元断言（改写后无违规字段）
