# 搜索链静默中断事故：三根因联合修复（2026-08-31）

## 事故现象

调研线程 `01a05669`（纯委派线程，GLM-5.3 / zhipu 通道）串行搜索到第 4 轮时
突然停止：无错误、无结论、UI 里搜索项却显示"Searched the web"（假完成）。
同日发现混合轮里 11 个孤儿搜索调用全部零重搜（2ms 透传 note）。

## 三根因（调研线程 01a05683 逐条实锤）

### R1：`SEARCH_CONT_MAX = 3` 超限静默终止（直接死因）

续轮判定 `rounds < SEARCH_CONT_MAX` 超限即 break：第 4 个串行搜索**不执行**，
done 帧按 `status:"completed"` 兜底 flush（rollout 实锤该调用
`started→completed` 仅 1ms），随后轮次静默结束。客户端对纯 web_search 收尾
不会自动续话——**任何"直接结束轮次"的路径都等于"看起来死了"**。

### R2：fallback 对纯委派线程恒为空（且完全静默）

`_fallback_query` 跳过所有 `<` 开头的 user 消息（本为剥 environment_context），
而纯委派线程唯一的实质消息是 `<codex_delegation>` XML——被整条误杀 →
fallback 恒空 → `_execute_search` 静默 return note，一行日志都没有。
该函数是请求侧 fulfill 与续轮引擎空 query 兜底**共用**的，两条路径同时受害。

### R3：历史 `web_search_call` 的 `action.query` 被入口转换器丢弃

客户端回传的历史 web_search_call 形状是 `{id, status, action:{query}}`——
**无 call_id、无 arguments**。`normalize_input_item` 只读 `arguments`/`input`，
action 被丢弃 → fulfill 取词只能靠 fallback → 撞上 R2。
现有测试 S6 用的是理想形状（call_id+arguments 都在），真实形状逃过回归。

## 修复（F1/F2/F3，分层防御，`kimi_bridge.py`）

| 修复 | 位置 | 内容 |
|---|---|---|
| F1 | `normalize_input_item` | args 为 None 且 `action.type=="search"` 且 query 非空时，从 `action.query` 恢复 `args={"query":…}`；优先级 `arguments > input > action`，additive 无回归面 |
| F2a | 新增 `_extract_delegation_text` | 非贪婪提取 `<codex_delegation>` 内首个 `<input>…</input>` 正文；畸形回落原文（维持既有 skip） |
| F2b | `_fallback_query` | `<codex_delegation>` 开头的消息先提取 `<input>` 正文再判断，委派线程兜底不再恒空 |
| F2c | `_execute_search` | 空查询+空兜底时 `log.warning` + `stats.note_event("web_search_no_query")`，静默路径清零 |
| F3a | `SEARCH_CONT_MAX` | 3 → 8（按轮计，每轮可并行多搜索） |
| F3b | gen() 续轮段 | **最后一轮**（第 8 轮搜索执行完后）follow-up 摘除 `web_search` 工具 + 注入收尾指令，逼模型基于已有材料写最终文本——1ms 假完成从机制上消除 |
| F3c | gen() 退出路径 | `stop_reason` 区分 `max_rounds` / follow-up 失败（防御分支，warning flush）；混合轮设计内 flush 保持静默（S4 锁定行为） |

关键设计：超限**绝不直接结束轮次**——先让第 8 轮搜索真实执行，再发一个
"无搜索工具 + 收尾指令"的 follow-up，保证每个 done 帧都对应真实执行过的
搜索，且模型必然产出非 web_search 的最终输出。

## 回归测试（`bridge/test_web_search_ux.py`，46/46 全绿）

新增三个用例锁死事故形状：

- **S7** rollout 真实形状（无 call_id/arguments、只有 action）+ 纯委派 XML
  消息 → 逐 call 精确重搜，query 与 `action.query` 一一对应；
- **S8** 委派 `<input>` 正文兜底 + 无查询时 warning/stats 可观测；
- **S9** SEARCH_CONT_MAX 用尽 → 最后一轮摘 web_search、注入收尾指令、
  每个搜索真实执行（mock 搜索数 == done 帧数）、干净 completed。

事故同构冒烟（与 14:10:15 完全相同的输入形状）：
修复前 fulfill 替换 0 / 搜索 0 → **修复后替换 3 / 搜索 3**。

## 教训

1. **假完成比报错更危险**——done 帧带 `completed` 状态但 1ms 完成，UI 与
   rollout 都"正常"，只有日志时间线能戳穿。兜底 flush 必须带原因可观测。
2. **入口/出口形状要成对测试**——出口补了 `action`（UX 修复），入口却
   不认 action（本次 R3），回流闭环断在半路。真实 rollout 形状（而非
   理想形状）必须进回归。
3. **fallback 的过滤规则要认得所有合法包装**——`<` 开头跳过一条规则
   误杀了整个委派线程生态；新增消息包装（delegation XML）时兜底链要同步。
